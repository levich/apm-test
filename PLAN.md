# План реализации Angie Proxy Manager 1.0

Согласованный план релиза. Заменяет прежний порядок выпуска из [первоначального плана](docs/archive/original-plan.md). Текущее состояние реализации — `0.1.0.dev0`; выполненные проверки и оставшиеся работы отражены в [протоколе проверок](docs/VALIDATION.md) и [матрице совместимости](docs/COMPATIBILITY.md).

## 1. Результат и границы релиза

Создать публичный open-source проект под **MIT**: панель управления Angie OSS и PRO для одного Linux-сервера с установкой через Docker Compose.

**Первый публичный релиз включает базовые функции и все согласованные группы расширений NPMPlus.** Промежуточные сборки используются для внутренних проверок. Предыдущая схема «расширения после первого релиза» заменяется этим планом.

Зафиксированные решения:

- Backend: Python 3.13, FastAPI, Pydantic, SQLAlchemy 2, Alembic.
- Интерфейс: Tabler Core, Tabler Icons, Jinja2, HTMX; русский и английский языки.
- Хранилище панели: SQLite. PostgreSQL и SQLite поддерживаются как **источники импорта**.
- Роли: администратор, оператор, наблюдатель.
- DNS: Webnames, Yandex Cloud DNS, REG.RU, Selectel API v2, Cloud.ru Evolution DNS.
- Все функции реализуются в панели; доступность конкретной функции определяется возможностями установленной сборки Angie.
- Базовая версия для начала разработки — Angie/Angie PRO 1.12.4. Версии образов, модулей и библиотек закрепляются в манифесте сборки. [Angie](https://angie.software/angie/docs/oss_changes/), [Angie PRO](https://angie.software/angie/docs/pro_changes/)

Референс пользовательских возможностей — [NPMPlus](https://github.com/ZoeyVid/NPMPlus). Собственный код реализуется на Python; зависимости сохраняют свои лицензии.

## 2. Архитектура и контракты

### Сервисы установки

| Сервис | Ответственность |
|---|---|
| `manager` | FastAPI, интерфейс, пользователи, политики, API и постановка заданий |
| `worker` | Применение конфигураций, сертификаты, Docker discovery, импорт и обслуживание интеграций |
| `angie` | Проксирование и локальный агент проверки/применения конфигурации |
| `docker-gateway` | Доступ только к необходимым операциям чтения Docker API |
| Дополнительные сервисы | CrowdSec/AppSec, GoAccess, GeoIP updater, Anubis, PHP-FPM |

`manager` и `worker` используют один образ приложения. Агент внутри контейнера Angie запускается вместе с сервером под надзором s6-overlay.

Целевая платформа — Linux с обычным Docker Engine, архитектуры amd64 и arm64. Angie использует host network: это позволяет добавлять TCP/UDP-порты через панель без изменения публикации портов Compose. Остальные сервисы работают в закрытой Docker-сети.

Панель доступна через отдельный HTTPS-listener Angie на порту 81. Backend публикуется только на loopback. Первый администратор создаётся с одноразовым setup-токеном, получаемым локальной CLI.

### API и модель данных

- Версионированный REST API `/api/v1`: маршруты, upstream-группы, списки доступа, сертификаты, DNS-профили, политики, пользователи, discovery, импорт, резервные копии и операции.
- HTML-формы и REST API используют общий сервисный слой, валидацию и проверки прав.
- Долгие операции возвращают идентификатор задания. Интерфейс показывает прогресс, ошибки и фактически применённую версию.
- Внутренний API агента работает через Unix socket: возможности сборки, проверка, применение, откат и статус. Произвольные команды и файловые пути через него не принимаются.
- Основные сущности: маршруты HTTP/redirect/stream, locations, upstream-группы, политики доступа/TLS/заголовков, сертификаты, DNS-профили, пользователи, сессии, задания, версии конфигурации и аудит.
- Каждый маршрут имеет источник управления: ручной, Docker или импорт. Автоматизация не перезаписывает объекты другого источника.
- Изменения защищаются от потери параллельных правок. Конфликт возвращается пользователю до применения.

### Применение конфигурации

Обычное сохранение запускает операцию «сохранить и применить»:

1. Сохранить желаемое состояние и задание одной транзакцией.
2. Создать неизменяемый комплект конфигурации с версионными ссылками на сертификаты.
3. Проверить комплект целевым бинарным файлом через `angie -t`.
4. Под единственной блокировкой переключить активную версию и выполнить reload.
5. Подтвердить новое поколение конфигурации и выполнить контрольные запросы.
6. Зафиксировать применённую версию либо восстановить предыдущий комплект.

Желаемое и применённое состояния хранятся отдельно. После сбоя worker сначала сопоставляет БД, файлы и состояние Angie. Неудачный откат останавливает дальнейшие применения и отображается как отдельная ошибка.

### Сертификаты и DNS

**Единый ACME-движок — Certbot в worker.** HTTP-01 использует общий webroot, DNS-01 — собственные Python-адаптеры через фиксированные authentication/cleanup hooks. Certbot работает в режиме `certonly`; конфигурацией Angie управляет только панель. [Документация Certbot](https://eff-certbot.readthedocs.io/en/stable/using.html)

Angie получает сертификаты через статические пути к PEM-файлам. Это заменяет предварительный вариант со встроенным ACME и переменными сертификатов: такой способ загрузки нужен для поддержки OCSP и сжатия сертификатов. [Ограничения загрузки сертификатов Angie](https://angie.software/angie/docs/configuration/modules/http/http_ssl/)

DNS-адаптеры имеют общий контракт: проверка доступа, поиск зоны, добавление TXT, подтверждение распространения и удаление конкретного значения. Состояние challenge сохраняется для восстановления после перезапуска. Чужие TXT-значения сохраняются; запросы Webnames сериализуются с учётом его лимитов.

### Доступ и секреты

- Серверные отзываемые сессии, HttpOnly/Secure cookies, CSRF-защита, ограничение попыток входа.
- Оператор управляет обычными маршрутами и разрешёнными профилями; наблюдатель читает доступные данные.
- DNS-секреты, произвольные директивы, пользователи, импорт и восстановление доступны администратору.
- Секреты шифруются ключом вне БД и исключаются из API-ответов и журналов.
- OIDC реализуется через готовую библиотеку; административные роли назначаются явно.
- Для включённой внешней авторизации и WAF поведение при недоступности сервиса задаётся политикой; исходное значение — отказ с временной ошибкой.

## 3. Последовательность реализации

Каждый этап заканчивается работающей контрольной сборкой и проверками.

| Этап | Работы | Критерий завершения |
|---|---|---|
| **0. Основа и технические проверки** | Монорепозиторий, MIT, зависимости, Compose, стандартный и расширенный образы Angie. Проверки агента, reload/rollback, Certbot, CrowdSec Lua bouncer и ECH | Подтверждены основные интеграции; составлена матрица возможностей OSS/PRO |
| **1. Каркас приложения** | БД и миграции, задания, аудит, пользователи и роли, сессии, setup, Tabler, локализация | Вход и права работают через UI и прямые API-запросы |
| **2. Базовая маршрутизация** | HTTP/HTTPS, WebSocket, locations, redirects, TCP/UDP, Basic Auth, IP/CIDR, административные snippets | Маршруты создаются и применяются; ошибочная конфигурация сохраняет рабочую версию |
| **3. Сертификаты и Docker** | HTTP-01, wildcard, пять DNS-провайдеров, собственные сертификаты, продление; Docker labels и reconciliation | Контейнер по меткам получает маршрут и HTTPS; перезапуски восстанавливают состояние |
| **4. Расширенные политики** | HTTP/2–3, gRPC, PROXY protocol, upstream-группы, stream TLS, mTLS, несколько ACL, TLS/ACME-профили, заголовки, лимиты, буферизация, Brotli/Zstd, IDN, default/dead hosts, статика/PHP | Возможности управляются формами и проходят реальные сетевые проверки |
| **5. Авторизация и защита** | OIDC, TOTP и recovery codes; Authelia, Authentik, OAuth2 Proxy, Tinyauth, VoidAuth; CrowdSec/AppSec, CAPTCHA, Anubis, GeoIP | Проверены разрешение, отказ, исключения и недоступность внешних сервисов |
| **6. Специальные возможности и аналитика** | ECH, сжатие сертификатов, OCSP, дополнительные модули, runtime-настройки, MPTCP/QUIC BPF, GoAccess, CLI восстановления, pre-run hooks | Каждая функция работает на заявленной сборке либо имеет проверенную причину недоступности |
| **7. Импорт и эксплуатация** | Импорт NPM/NPMPlus из SQLite/PostgreSQL, backup/restore, обновление, документация, multiarch-сборки | Подтверждены перенос и восстановление на чистом сервере |
| **8. Приёмка 1.0** | Полная матрица функций, регрессия OSS/PRO, проверка установки и обновления | Все обязательные критерии релиза выполнены |

Внутри этих этапов фиксируются следующие правила:

- **Docker labels:** сохраняется пространство `apm.*`; используются ссылки на заранее созданные DNS-профили. Конфликты доменов показываются без перезаписи. Discovery сочетает события и периодическое полное сопоставление. Создание A/AAAA-записей автоматически не включается.
- **ACL:** интерфейс показывает порядок, наследование host/location и итоговое правило. Импорт активируется только при сохранении исходной семантики доступа.
- **CrowdSec:** запросы обрабатываются в Angie через проверенный Lua bouncer; FastAPI не включается в путь клиентского трафика.
- **ECH:** расширенный образ, управляемая ротация ключей и отдельная возможность DNS-адаптера для HTTPS records. При отсутствии такого API используется подготовка записи и подтверждение её публикации перед переключением.
- **Модули:** стандартный образ использует совместимые пакеты Angie; расширенный OSS-образ собирает необходимые компоненты из закреплённых исходников. PRO использует лицензированные пакеты и совместимые модули.
- **Импорт PostgreSQL:** отдельная CLI читает источник в согласованном read-only snapshot и создаёт переносимый архив. Подключение к исходной БД не сохраняется в панели.
- **Импорт:** сначала отчёт и черновики, затем проверка полного комплекта. Неизвестная схема или непереносимая защита блокирует активацию затронутых объектов.
- **Обновление:** перед миграцией создаётся резервная копия; возврат выполняется предыдущим образом и восстановлением соответствующей копии.

## 4. Проверки и готовность релиза

Проверки объединяются в четыре набора:

- **Модульные:** валидация, генерация конфигурации, права, наследование политик, нормализация IDN, DNS-адаптеры и преобразования импорта.
- **Интеграционные:** настоящий Angie OSS/PRO, HTTP/gRPC/TCP/UDP-сервисы, ACME test server, PostgreSQL-источник, Docker events, OIDC и CrowdSec.
- **Браузерные:** установка, вход, создание маршрута, HTTPS, управление доступом, ошибки применения, импорт, смена языка и восстановление.
- **Сбойные:** завершение процессов на шагах применения, потеря событий Docker, ошибки DNS/API, истечение токенов, недоступность IdP/WAF, неудачное обновление.

Обязательные сценарии приёмки:

1. Чистая установка Compose и создание первого администратора.
2. Все согласованные маршруты и политики работают на заявленных сборках.
3. Выпуск и обновление wildcard проверены для каждого из пяти DNS-провайдеров.
4. Ошибочные и конкурентные изменения сохраняют последнюю рабочую конфигурацию.
5. Прямые API-запросы не обходят роли и ограничения административных настроек.
6. AppSec проверяет тела HTTP/1.1–3; ограничения streaming и буферизации отражены в UI.
7. Импорт SQLite/PostgreSQL сохраняет доступ, сертификаты и связи поддерживаемых объектов.
8. Backup/restore восстанавливает установку на другом чистом сервере.
9. Для каждой из 25 групп NPMPlus есть реализация, проверка и запись в матрице совместимости.

## 5. Допущения, зависимости и сроки

- Рабочее название — **Angie Proxy Manager**.
- Хранилище новой панели — SQLite; PostgreSQL используется для импорта.
- Стандартные значения: совместимые TLS 1.2/1.3; HSTS, ECH, WAF и сетевые оптимизации включаются явно. Access logs настраиваются отдельно от аудита изменений.
- Управление несколькими серверами, Kubernetes и MariaDB/MySQL-импорт в 1.0 не входят.
- Для приёмки нужны лицензированная PRO, тестовые DNS-зоны пяти провайдеров и исходные снимки поддерживаемых схем NPM/NPMPlus.
- Промежуточная рабочая сборка ориентировочно появится через **1–2 недели**.
- Для одного опытного разработчика с полной занятостью ориентир первого публичного релиза со всем объёмом — **4–7 месяцев**. Оценка пересчитывается после этапа 0 по результатам интеграционных проверок.
