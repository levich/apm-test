## Не подтверждено

- При первоначальных испытаниях Docker Engine API не отвечал. Затем собраны manager и локальный Angie из закреплённого исходника, проверены s6 и полный Compose с bridge на Docker Desktop arm64. Официальная базовая OCI-сборка Angie, extended, Linux host network и сценарий обновления/restore полной поставки требуют отдельной приёмки.
- Реестр `docker.angie.software` завершает TLS-соединение тайм-аутом из текущего окружения. Версия Angie зафиксирована тегом; OCI digest этого образа остаётся неподтверждённым.
- Проверка нативной arm64-сборки Angie не заменяет целевые Linux amd64/arm64 и PRO.
- DNS-тесты используют `httpx.MockTransport`: проверяют формат запросов, сохранение посторонних TXT и cleanup, но не актуальные права/лимиты реальных аккаунтов.
- Нет лицензии PRO, пяти тестовых DNS-зон, реальных IdP/WAF и исходных снимков NPM/NPMPlus. Эти проверки требуют внешнего стенда.
- ACME test server, выпуск/продление wildcard, ECH handshake, сжатие сертификатов, расширенные модули, AppSec body matrix, GeoIP/GoAccess и полный fault injection остаются критериями 1.0.

Точный остаток реализации указан в [матрице](COMPATIBILITY.md); текущая сборка не объявлена 1.0.

После обнаруженного тайм-аута QUIC исправлены UDP listeners с `reuseport`. Повторный прогон сохранён в [angie-checks.json](angie-checks.json).

## Режим существующего Angie

Добавлены самостоятельный Compose, пример env, systemd-агент и [инструкция подключения](EXISTING_ANGIE.md). Проверены 42 теста и Ruff. Новый сценарий запускается командой:

```sh
PYTHONPATH=src uv run --no-sync python scripts/check_existing_angie.py \
  --binary /path/to/angie --conf-dir /path/to/conf --work ./test-results/existing-angie
```

Он использует временную директорию и высокие локальные порты. После изменений compiler также повторно пройден штатный `scripts/check_angie.py`: HTTP, TLS, gRPC/HTTP2, HTTP3/QUIC, TCP, UDP и сохранение трафика при ошибке. Проверка `compose config` выполнялась с подстановкой `.env.existing.example`.

Дополнительно выполнен `docker build -t apm-manager:existing-check .` и изолированный Compose smoke на Docker Desktop Linux arm64. Для smoke источник данных заменён временным named volume, порты manager убраны, агент запущен из того же образа под `0:10001`. Проверены init, health manager, подключение worker UID 10001 к root-агенту по Unix socket и получение setup-token без вывода токена в протокол. Агент в этом smoke не запускал Angie. Контейнеры, сеть и тестовый том удалены.

Полная связка контейнеров с системным Angie, systemd, bind mount и политиками SELinux/AppArmor на Linux остаётся отдельной приёмкой. Нативный сетевой сценарий и контейнерный smoke подтверждают разные части поставки; поведение PRO не проверено.

## Локальный Compose с Angie

Для Docker Desktop добавлен `compose.local.yaml`: bridge вместо host network, backend `manager:8181` одинаков у агента и worker, общий named volume, публикация портов только на loopback. В базовый Compose добавлена проверка готовности Angie через `/status` Unix-агента; worker ожидает её успешного завершения.

Из-за TLS timeout официального реестра базовый Angie собран через `deploy/local/Dockerfile` из архива 1.12.4 с SHA256 из `build/sources.lock.json`, затем использован штатным `deploy/angie/Dockerfile` с s6. Сборки `apm-manager:dev` и `apm-angie:dev` завершены успешно на Linux arm64.

На отдельном проекте `apm-local-acceptance` пройден сценарий:

```sh
PYTHONPATH=src uv run --no-sync python scripts/check_compose.py \
  --compose-file compose.yaml --compose-file compose.local.yaml \
  --project-name apm-local-acceptance --http-url http://127.0.0.1:8088 \
  --upstream-host apm-local-test-backend
```

Backend для этого сценария запускался в том же control network и возвращал `apm-compose-upstream` на порту 19080. Проверены setup, очередь apply, настоящий HTTP через Angie и отклонение неверной директивы с сохранением трафика. Обнаруженный разный backend URL у агента и worker исправлен в локальном профиле; повторный полный сценарий прошёл. После проверки тестовый проект, backend и его том удалены. Для пользователя запущен отдельный чистый `angie-proxy-manager-local` без тестовых пользователей и маршрутов. Повторно проходят 42 теста и Ruff.

Этот прогон подтверждает локальный bridge-профиль; bind mounts, production host network, extended-модули, HTTP/3 в контейнере, amd64 и PRO здесь не проверялись.

У финального локального экземпляра проверены healthy manager/Angie, успешное начальное apply и отсутствие пользователей/ресурсов. Chromium открыл `https://localhost:81`, показал форму первоначальной настройки без JavaScript-ошибок; снимок сохранён локально в `test-results/local-compose/setup.png`.

## Вкладки прокси-хоста и запрос сертификата

Формы создания и редактирования разделены на «Основное», «Пути», «SSL» и «Дополнительно». SSL объединяет выбор существующего сертификата и запрос нового: email, HTTP-01/DNS-01, DNS-профиль, условия CA. Wildcard выбирает DNS-01; обычное редактирование сохраняет существующую привязку без повторного выпуска. Доступны RU/EN, клавиатурное переключение вкладок и раскрытие скрытой вкладки с ошибкой валидации.

Пройдены 48 pytest-тестов, Ruff, `node --check` и расширенный `scripts/browser_check.py` на отдельном пустом каталоге с API без worker. Chromium подтвердил создание и редактирование хоста, сохранение timeout и location между вкладками, постановку HTTP/DNS-сертификатов, сохранение привязки, обязательное согласие, мобильный диалог и отсутствие JS/HTTP ошибок. Дополнительно проверены мобильная кнопка сохранения без переполнения и тёмная тема. Скриншоты находятся в локальном `test-results/proxy-editor/browser/`.

Браузерный стенд не обращался к центру сертификации: выпуск остался в очереди без worker. Реальный выпуск Let's Encrypt для публичного домена, DNS/API и доступность внешнего порта 80 этим UI-прогоном не подтверждаются.

Скриншоты: локальный `test-results/field-help-check2/browser/`. 48 pytest-тестов, Ruff и `node --check` проходят.
